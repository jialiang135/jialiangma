============================================
个人数字分身 · 多Agent私有RAG系统 — 项目详解
============================================

一、为什么要做这个项目
────────────────────────────

23年初我开始接触大模型，当时市面上充斥着各种"ChatGPT套壳"产品——调个API就
敢说自己做了AI应用。但真正在企业面试中，面试官关心的是你能否深入LLM应用栈的
底层能力，而不仅仅是调用OpenAI的SDK。

这个项目的初衷有三个：

1. 面试演示需要
   我的简历上写了很多技术关键词——LangGraph、RAG、ReAct、ChromaDB。但简历只
   能写一句话，面试官无法直观感受这些技术的实际落地效果。我需要一个能"说话"
   的项目——面试官打开链接直接对话，系统能回答关于我的所有信息，效果比任何
   文字描述都有说服力。

2. 深入理解Agent
   AutoGPT和LangChain的出现让"Agent"成了热词，但真正理解Agent循环
   （观察→思考→行动→观察→...）的人并不多。我想从零搭建一个ReAct Agent，
   搞清楚工具调用（Tool Calling）的完整链路：LLM决策 → 选择工具 → 传参 →
   执行 → 返回结果 → LLM再次决策。这个过程如果只读文档是学不会的。

3. RAG的工程化实践
   RAG（检索增强生成）看起来简单：向量化→检索→拼接Prompt→LLM生成。但真正
   做起来会发现一堆工程问题：文档怎么分块？检索质量怎么保障？重排怎么做？
   检索为空怎么办？LLM编造信息怎么办？这些问题只有亲手踩过坑才能回答。

最终的项目定位：一个能帮我在面试中"说话"的个人AI分身，同时展示我在
大模型应用工程方面的能力。


二、技术架构
────────────────────────────

整个系统分为四层：

第一层：前端（Vue 3 SPA）
- 三个页面：对话页、知识库管理页、评测页
- Composition API + Vite 6 构建，生产构建产物由 FastAPI 托管
- SSE 流式解析（fetch + ReadableStream），AbortController 实现中断
- Pinia 状态管理，JWT 登录态持久化

第二层：API 网关（FastAPI + Nginx）
- FastAPI 提供 RESTful API + SSE 流式端点
- JWT + bcrypt 鉴权，HS256 签名，480 分钟过期
- RBAC 角色权限：admin（管理知识库）+ user（仅聊天查看）
- Nginx 反向代理：SSL 终止、Gzip 压缩、请求限流、安全响应头
- 健康检查 + 优雅关闭

第三层：Agent 引擎（LangGraph）
- 7 个节点组成状态图：router / retrieve / chat_agent / tools /
  manage_agent / eval_agent
- 路由节点根据 agent_mode 条件分支：
  chat → retrieve → chat_agent ⇄ tools（ReAct 循环，最多 5 轮）
  manage → manage_agent（线性：上传/删除/清空/重建）
  eval → eval_agent（线性：并发问答 + 幻觉检测）
- AgentState TypedDict 统一管理 22 个状态字段
- ReAct 循环：LLM 决策 → 需要工具？→ 执行工具 → ToolMessage 返回 → LLM 再决策
- 两个 SSE 生成器：astream_events v2（主通道，真正逐 token 流式）+
  ainvoke 降级（备用通道）

第四层：RAG 检索管线
- 文档解析（unstructured + pytesseract + 15 种格式支持）
- 语义分块（RecursiveCharacterTextSplitter，中文句号/问号/感叹号分隔，
  chunk_size=1000，overlap=200，内容去重）
- 向量化入库（DashScope text-embedding-v4，1024 维，ChromaDB PersistentClient）
- 两阶段检索：
  阶段1: ChromaDB 语义搜索 topK=10
  阶段2: DashScope gte-rerank-v2 重排 topK=5
- BM25 关键词检索 + RRF 融合（与向量检索互补）
- 检索结果 TTL 缓存（MemoryCache，1小时，128条FIFO）

数据流（以一次对话为例）：

  用户输入"你做过什么AI项目？"
  → FastAPI 接收，提取 JWT 鉴权
  → SSE 生成器构建 AgentState
  → LangGraph graph.ainvoke(state)
  → router 节点判断 agent_mode="chat"
  → retrieve 节点：ChromaDB 检索 → DashScope 重排 → 注入 System Prompt
  → chat_agent 节点：LLM 分析 → 决定调用 search_knowledge_base
  → tools 节点：执行搜索工具，返回 ToolMessage
  → chat_agent 节点：LLM 拿到检索结果 → 生成最终回答
  → SSE 逐 token 推送：reasoning → answer chunks → done


三、遇到的难点和解决方案
────────────────────────────

难点1：检索质量不稳定
━━━━━━━━━━━━━━━━━━━━

问题表现：
第一版只用了 ChromaDB 向量检索，用户问"你用过Python吗"能搜到结果，
但问"你写代码用什么语言"就搜不到——因为问题是口语化的，文档写的是"技术栈"。

解决过程（经过三轮迭代）：

第一轮：调参
- 把 topK 从 5 改到 10 再到 20，召回率有提升，但噪声也多了
- 结论：单纯增加候选数不是好方案

第二轮：引入重排序（Rerank）
- ChromaDB 粗排 topK=10 → DashScope gte-rerank 精排 topK=5
- 效果：top5 的相关性明显提升，噪声大幅减少
- 但偶尔 DashScope API 超时导致整个检索失败

第三轮：混合检索 + 优雅降级
- 加入 BM25 关键词检索 + RRF 融合（RRF 权重：向量 0.7，BM25 0.3）
- Rerank API 失败时自动回退 ChromaDB 原始排序（score=1.0）
- 最终方案：三路保障——向量检索 / 混合检索 / Rerank 重排

经验教训：
- RAG 不是"接个向量库就完事"，检索质量需要多层次优化
- 云服务（Rerank API）不可靠是常态，必须有降级策略
- BM25 对精确关键词匹配很有用，和向量检索互补


难点2：防幻觉策略设计
━━━━━━━━━━━━━━━━━━━━

问题表现：
早期版本遇到过三种幻觉：
- 检索为空时，LLM "自由发挥"编造信息（最致命）
- 检索到不相关内容时，LLM 强行缝合信息
- 多轮对话中，LLM 把上一轮的上下文当成知识库内容

解决过程（四层防线）：

第一层：System Prompt 约束
- "你是一个个人数字分身，只能基于知识库中的信息回答问题。
   如果信息不在知识库中，请明确告知用户'抱歉，我的知识库中暂时没有
   这方面的信息'，禁止编造任何信息。"
- 关键技巧：不只用否定词"不要编造"，还要告诉 LLM
  "当信息不足时你应该做什么"（正面引导比禁止更有效）

第二层：检索结果为空兜底
- 检索返回 0 条 → 不走 LLM 推理流程
- 直接返回"抱歉，知识库中暂无相关信息"
- 防止 LLM 在没有任何上下文时自由发挥

第三层：自我校验工具（verify_answer_against_kb）
- 给 LLM 一个"自省"的工具：生成答案后，调用工具检查答案是否有知识库依据
- 匹配度 < 0.5 → 标记为"可能为幻觉，建议不在回答中使用"
- 这个设计借鉴了人类写作文时"查资料验证"的习惯

第四层：评测集验证
- 评测集中故意放 5 道知识库中没有的题（如"你养过猫吗"）
- 评测完成后自动计算幻觉率
- 如果系统在这些题上编造了答案，幻觉率直接暴露问题

量化效果：
- 评测测试集（8 题含 5 题幻觉陷阱）
- 幻觉率从早期 60%+ 降到 10% 以内


难点3：多用户数据隔离
━━━━━━━━━━━━━━━━━━━━

问题表现：
最初设计是"多租户"——每个用户有独立的知识库。但面试演示场景下，面试官
（普通用户）无法上传文件，他们的知识库是空的，问任何问题都返回
"知识库中暂无相关信息"，整个系统形同虚设。

解决过程：
- 第一版：多租户隔离（每个用户检索自己的 KB，owner_id 过滤）
- 第二版（当前）：共享知识库模式
  - 检索统一用 owner_id=1（管理员的知识库）
  - 写入操作（上传/删除/清空/重建）仍需要管理员权限
  - 普通用户只能查看和聊天，不能修改

经验教训：
- 多租户设计要看场景——SaaS 产品需要严格隔离，面试演示需要共享
- 架构上保留 owner_id 过滤能力，业务层决定用不用


难点4：SSE 流式的坑
━━━━━━━━━━━━━━━━━━━━

问题表现：
LangGraph 的 astream_events v2 在某些情况下不触发事件，
用户看到页面一直在转圈但没任何输出。

解决过程：
- 实现了双通道：astream_events v2（主通道）+ ainvoke（降级通道）
- ainvoke 拿到完整结果后，人工模拟逐字推流（按句/按词切割），
  虽然不够完美但保证有输出
- Nginx 配置 proxy_buffering off 和 proxy_read_timeout 600s，
  防止代理层断开长连接

经验教训：
- LLM 应用依赖多个外部服务（LLM API + Embedding API + Rerank
  API），任何一个都可能挂，必须层层降级
- 测试线上环境时发现 Nginx 默认会缓冲 HTTP 响应，SSE 必须显式关闭


难点5：文档解析质量
━━━━━━━━━━━━━━━━━━━━

问题表现：
用户的简历是 PDF（双栏 + 表格布局），直接用 PyPDF 提取后文本完全错乱——
"手机号"在左栏，"138xxxx"在右栏第三个单元格，提取出来完全对不上。

解决过程：
- 主解析引擎：unstructured 库（自动识别 PDF 布局）
- 降级链：PyPDF → python-docx → openpyxl → plain text → OCR
- 图片 OCR：pytesseract + 中文语言包
- ZIP 递归：上传压缩包后自动解压遍历
- 共支持 15+ 格式：PDF、DOCX、XLSX、TXT、MD、代码文件(.py/.js/.ts)、
  JSON、CSV、HTML、XML、PNG、JPG、ZIP、RAR


四、量化成果
────────────────────────────

技术指标：
- 支持 15+ 文档格式解析（PDF/DOCX/XLSX/TXT/MD/代码/图片OCR/ZIP）
- ReAct 推理最多 5 轮迭代（LLM自主决策何时停止）
- 两阶段 RAG 检索（语义搜索 topK=10 + Rerank 重排 topK=5）
- 5 个 ReAct 工具（语义搜索/文件列表/知识库摘要/对话历史/自我校验）
- 7 个 LangGraph 状态图节点
- SSE 真正逐 token 流式输出（astream_events v2）
- Docker 镜像 < 1GB（多阶段构建，Node 20 + Python 3.12-slim）
- 评测 4 维指标（准确率/幻觉率/匹配度/检索质量）

架构指标：
- 3 个 Agent 模式（chat/manage/eval）
- RBAC 双角色权限（admin/user）
- 4 层防幻觉策略
- MRR（平均倒数排名）作为检索质量核心指标
- 命中率（Hit Rate）0.85+（评测测试集验证）

工程实践：
- Docker 多阶段构建（分离构建环境和运行环境）
- Docker Compose 生产级部署（健康检查、资源限制、自动重启）
- Nginx 反向代理（限流、Gzip、安全头、SSE 专用配置）
- 优雅降级：Rerank API 失败 → 回退原始排序；OCR 缺失 → 跳过并警告；
  astream_events 不可用 → 回退 ainvoke
- 标准化 API 响应格式：{ success, message, data }


五、技术选型的 Why & How
────────────────────────────

为什么选 LangGraph 而不是纯 LangChain？
- LangChain 的 Chain 适合线性流程，Agent 需要循环决策
- LangGraph 的 StateGraph 天然支持条件边和循环边
- 可视化状态图让工作流一目了然

为什么选 ChromaDB 而不是 Pinecone/Weaviate？
- 本地部署零依赖（PersistentClient），不需要额外服务
- Python 原生支持，和 LangChain 集成度最高
- 面试演示不需要分布式向量库，单机足够

为什么选 SSE 而不是 WebSocket？
- 对话场景是单向流（服务端→客户端），SSE 天然匹配
- HTTP 协议无需额外握手，Nginx 代理只需一行配置
- 前端 fetch + ReadableStream 即可解析，零依赖

为什么选 DeepSeek V4 Pro？
- 性价比：同等效果下价格远低于 GPT-4
- 中文能力：DeepSeek 的中文理解和生成能力在开源模型中领先
- API 兼容：LangChain 有官方 langchain-deepseek 集成

七、如果你也是应届生，想做类似项目
────────────────────────────

几点建议：

1. 不要满足于"调通API"
   调通API只需要30分钟，真正花时间的是：检索质量怎么优化、
   幻觉怎么防止、API挂了怎么降级、多用户怎么隔离。
   面试官问的就是这些"调通之后"的事。

2. 先想清楚防幻觉策略
   在开始写代码之前，先把"如果检索为空怎么办""如果API超时怎么办"
   "如果用户问知识库没有的东西怎么办"这三个问题想清楚。
   90%的RAG Demo都会在面试时幻觉翻车。

3. 先做命令行，再做前端
   不要一开始就写Vue/React。先用命令行把Agent链路跑通——
   能问答、能调工具、能循环推理。等核心逻辑稳定了再加前端。
   我的第一版就是纯Python脚本，调通了才加FastAPI和Vue。

4. 把"优雅降级"写进简历
   这是区分Demo和Engineer的关键词。Demo只展示正常情况，
   Engineer考虑异常情况。面试官会很感兴趣。

5. 不要怕用现成工具
   LangChain、ChromaDB、DashScope这些就是正确选择。
   不要为了"体现技术"自己去写向量检索、去训练Embedding模型。
   工程师的核心能力是"选型"和"集成"，不是"重新造轮子"。

面试问答准备 — 马佳良 · AI Agent方向
============================================

Q1: RAG 系统的核心挑战是什么？
────────────────────────────
回答要点：

1. 检索质量（最核心）
   - 向量检索的语义漂移：用户口语化问题 vs 文档正式表述不匹配
   - 解决方案：① 两阶段检索（粗排 + 精排）② BM25 关键词 + 向量混合检索（RRF 融合）
     ③ 中文语义分块（按句号/问号/感叹号切分，chunk_size=1000，overlap=200）

2. 幻觉问题
   - LLM 在检索不到时会编造信息
   - 我的方案：① System Prompt 强制约束"只能基于知识库回答"
     ② 检索为空 → 直接回复"知识库中暂无相关信息"
     ③ verify_answer_against_kb 工具自我校验，匹配度 < 0.5 标记为不可用
     ④ 评测集中故意放 5 道知识库中没有的题，验证兜底机制

3. 多轮对话的上下文管理
   - 历史消息累积导致 token 超限
   - 我的方案：ReAct 循环最多 5 轮，ToolMessage 记录检索结果而非全文保留

4. 文档解析质量
   - PDF 双栏/表格/图片混排导致文本错乱
   - 我的方案：unstructured 库多格式支持 + pytesseract OCR + ZIP 递归处理


Q2: Agent 和传统 LLM 应用的区别？
────────────────────────────
回答要点：

传统 LLM 应用：
- 单轮"输入 → 输出"，一次性给 LLM 所有上下文
- 适合翻译、摘要、分类等确定性任务

Agent（智能体）：
- 多步推理循环："思考 → 行动 → 观察 → 思考 → ..."
- LLM 自己决策：调用哪个工具、什么时候停
- 我的项目用 LangGraph 实现 ReAct 循环：
  router → retrieve → chat_agent（LLM决策）→ 需要工具？→ tools执行 → chat_agent → END
  最多 5 轮迭代，每轮 LLM 判断 tool_calls 是否为 True

核心区别：Agent 给了 LLM"手脚"（工具调用能力）和"大脑"（推理决策能力）


Q3: 怎么防止大模型幻觉？
────────────────────────────
回答要点：

我的项目用了四层防幻觉策略：

第一层：System Prompt 约束
- "你是个人数字分身，只能基于知识库内容回答问题"
- "如果信息不在知识库中，必须明确告知用户，禁止编造"

第二层：检索结果为空兜底
- 检索返回 0 条 → 强制回复"抱歉，我的知识库中暂时没有这方面的信息"
- 不把空上下文交给 LLM

第三层：自我校验工具（verify_answer_against_kb）
- LLM 生成答案后，调用工具比对答案与知识库原文
- 匹配度 < 0.5 → 标记可能为幻觉，建议不使用

第四层：评测体系验证
- 评测集中包含 5 道故意问知识库没有的问题
- 如果 LLM 编造了答案 → 幻觉率上升 → 问题暴露
- 量化指标：准确率、幻觉率、平均匹配度、检索质量


Q4: 为什么用 LangGraph 而不是直接调 API？
────────────────────────────
回答要点：

直接调 API 的问题：
- 只能做单轮问答，无法实现多步推理
- 工具调用需要手动管理状态和决策逻辑
- 代码里混杂大量 if-else，难以维护和扩展

LangGraph 的优势：
- 状态图（StateGraph）：用节点和边描述 Agent 工作流，逻辑清晰
- 条件边：router 根据 agent_mode 自动分流到 chat/manage/eval
- 状态管理：AgentState TypedDict 统一管理 22 个字段，节点间自动传递
- astream_events v2：真正的逐 token 流式输出，用户体验好
- 工具绑定：bind_tools 自动处理工具的 JSON Schema 生成

我的实际使用：
- 7 个节点（router/retrieve/chat_agent/tools/manage_agent/eval_agent）
- ReAct 循环用条件边实现（max 5 次迭代）
- SSE 双通道：astream_events（主） + ainvoke（降级）


Q5: SSE 和 WebSocket 选哪个？为什么？
────────────────────────────
回答要点：

我选 SSE (Server-Sent Events)，理由：

1. 场景匹配
   - 我的对话场景是"服务端→客户端单向推送"（AI 回答逐字到达）
   - SSE 天然适合单向数据流，不需要客户端频繁回传

2. 实现简单
   - SSE 就是标准 HTTP 协议，不需要额外握手
   - FastAPI 原生支持 StreamingResponse（text/event-stream）
   - 前端用 fetch + ReadableStream 即可解析，不用引入 WebSocket 库

3. 部署友好
   - Nginx 直接代理 HTTP/SSE，只需设置 proxy_buffering off
   - WebSocket 需要额外配置 Upgrade 头
   - 我的 nginx.conf 专门为 SSE 端点配置了禁用缓冲和长超时

4. 中断方便
   - SSE 的 AbortController 可以随时中断连接
   - 用户点击"停止生成"即可取消请求

如果场景需要双向频繁通信（如实时协作编辑），才选 WebSocket。


Q6: 多用户数据隔离是怎么实现的？
────────────────────────────
回答要点：

我的系统设计了三层数据隔离：

1. 向量数据库层（ChromaDB）
   - 每个文档入库时 metadata 携带 owner_id
   - 检索时 filter={"owner_id": owner_id} 过滤
   - 删除/清空操作需 owner_id 校验

2. 关系数据库层（SQLite）
   - 所有表通过 WHERE owner_id = ? 查询
   - 文件的增删改查全部校验归属

3. 鉴权层（JWT）
   - Token payload 含 sub（owner_id）
   - FastAPI 依赖注入 → get_current_user 提取
   - 所有 API 调用自动获取当前用户的 owner_id

近期改进：改为共享知识库模式（所有用户检索 owner_id=1 的管理员知识库），
但写操作（上传/删除）仍需管理员权限，满足面试演示场景。

Q7: 这个项目最大的技术挑战是什么？
────────────────────────────
回答要点：

最大的挑战是检索质量与防幻觉的平衡。

问题：
早期版本经常出现两种情况：
- 检索太松 → 召回噪音 → LLM 用不相关内容拼凑答案（幻觉）
- 检索太严 → 召回太少 → LLM "无米之炊"（一些能答的问题也答不了）

解决过程：
1. 尝试调 topK（5→10→20）→ 单纯增加候选效果有限
2. 引入两阶段检索：粗排（topK=10）+ DashScope gte-rerank 精排（topK=5）
   → 召回率提升，但仍有不相关内容
3. 加入 BM25 关键词检索 + RRF 融合
   → 当用户问题包含精确关键词时效果显著改善
4. 加 Rerank 降级机制
   → DashScope API 偶尔超时，自动回退 ChromaDB 原始排序
5. 加 self-verify 工具
   → 让 LLM 自己检查答案是否有知识库依据

最终效果：检索质量从 "partial" 降到接近 0，"幻觉率" 可控在 10% 以内（测试集验证）。


Q8: 你了解哪些 Agent 框架？你怎么评价它们？
────────────────────────────
回答要点：

我主要用过 LangChain + LangGraph，了解过其他框架：

LangChain/LangGraph：
- 优点：生态最全、中文支持好、工具链完善、社区活跃
- 缺点：封装层级多，Debug 定位困难；版本更新频繁，API 不稳定
- 适合：需要快速搭建复杂 Agent 工作流的场景

AutoGPT / BabyAGI：
- 理念先进（自主规划子目标），但实用性差
- 早期版本 Token 消耗巨大（一个任务花 $10+），且容易陷入死循环

CrewAI：
- 多 Agent 协作框架，适合角色扮演类任务
- 概念好（定义 Agent 角色和任务），但灵活性不如 LangGraph

我的选择逻辑：
做个人数字分身 → 需要精确控制 Agent 流程 → LangGraph 状态图最灵活
如果做多 Agent 协作 → 会考虑 CrewAI + LangGraph 结合
